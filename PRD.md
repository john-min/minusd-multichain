# MinUSD Multichain — Product Requirements Document

**Status:** Draft 1  
**Project:** `minusd-multichain`  
**Product name:** MinUSD  
**Token symbol:** `MINUSD`  
**Target networks:** Base Sepolia and Solana Devnet  
**Audience:** Project owner, contributors, reviewers, and prospective employers  

## 1. Executive summary

MinUSD is a public, testnet-only programmable-dollar prototype implemented independently on an EVM network and Solana. It demonstrates how a wallet or fintech could issue a branded digital-dollar token, enforce administrative controls, distribute simulated rewards, redeem the token for mock collateral, and reconcile supply across two different blockchain architectures.

The project is primarily an engineering and Solutions Architecture portfolio exercise. It should prove that the author can:

- Read, write, test, deploy, and debug basic smart-contract code.
- Explain the lifecycle of a stablecoin-like asset from acquisition through redemption.
- Compare EVM contracts with Solana programs using working implementations.
- Translate a product use case into contracts, transaction flows, acceptance criteria, operational controls, and technical documentation.
- Diagnose failed or unexpected transactions using explorers, logs, events, state, and application telemetry.

MinUSD is not a real stablecoin, is not backed by fiat or real reserve assets, and must never be marketed as production-ready or redeemable for money.

## 2. Problem statement

Reading blockchain documentation can provide vocabulary without producing the technical judgment expected of a customer-facing Solutions Architect. A credible technical portfolio project should require the author to make and explain concrete decisions involving:

- Token issuance and redemption.
- Contract permissions and allowances.
- Administrative roles, pauses, and account restrictions.
- Reserve and supply accounting.
- EVM and Solana execution models.
- Cross-chain messages and replay protection.
- Transaction debugging and operational handoffs.

MinUSD creates a bounded environment in which to develop and demonstrate that judgment without handling real customer funds.

## 3. Product thesis and use case

The fictional customer is **MinWallet**, a wallet and fintech product that wants a branded test dollar for use in its application.

Users should be able to:

1. Acquire MINUSD using a mock USDC asset.
2. Hold and transfer MINUSD between wallets.
3. Redeem MINUSD for the same quantity of mock USDC, subject to available test collateral.
4. Use MINUSD on Base Sepolia or Solana Devnet.
5. View the status and effects of every transaction.

The MinWallet treasury should be able to claim simulated rewards generated by the product. Authorized operators should be able to pause the system and freeze specific accounts for demonstration purposes.

This wallet use case is the primary narrative because it connects stablecoin mechanics to payments, customer balances, compliance controls, treasury economics, and multichain distribution. A DeFi vault may be added later as a focused extension, but it is not part of the first MVP.

## 4. Goals

### 4.1 Product goals

- Implement an end-to-end test token lifecycle on Base Sepolia.
- Implement equivalent product behavior natively on Solana Devnet.
- Make supply, collateral balances, permissions, and transaction outcomes observable.
- Demonstrate a controlled cross-chain burn-and-mint workflow after both single-chain implementations are stable.
- Produce documentation that a customer, salesperson, product manager, or integrations engineer could follow.

### 4.2 Learning goals

- Become comfortable with Solidity, Foundry, ERC-20 behavior, events, custom errors, modifiers, and contract calls.
- Become comfortable with Rust, Anchor, Solana accounts, PDAs, instructions, CPIs, SPL Token or Token-2022, and transaction logs.
- Understand the practical distinction among minting, burning, transferring, approving, swapping, wrapping, bridging, and redeeming.
- Learn to trace both successful and failed EVM and Solana transactions.
- Practice defining launch scope, dependencies, acceptance criteria, security assumptions, and operational ownership.

### 4.3 Portfolio goals

- Allow a reviewer to understand the architecture in under five minutes.
- Allow a reviewer to run the automated tests and a local demo from documented commands.
- Provide public testnet transaction examples for successful and reverted flows.
- Include a concise architecture decision record explaining major tradeoffs.
- Support a five-to-ten-minute narrated demonstration.

## 5. Non-goals

The initial project will not:

- Hold real fiat, USDC, USDT, or other assets with monetary value.
- Promise price stability, fiat redemption, yield, or regulatory compliance.
- Deploy to an EVM mainnet or Solana mainnet-beta.
- Integrate with banks, custodians, KYC providers, or real issuers.
- Recreate M0, Circle, Bridge, Wormhole, or another production protocol.
- Build a trust-minimized or production-grade bridge.
- Build an AMM, DEX, order book, or market-making system.
- Implement a production oracle, proof-of-reserves system, or validator network.
- Optimize for gas, throughput, or production-scale availability before correctness and clarity.
- Build a polished consumer frontend in the MVP.

## 6. Safety and public-project boundaries

Every user-facing document must state:

> MinUSD is an educational, testnet-only prototype. It is unaudited, has no monetary value, is not backed by real reserves, and is not redeemable for fiat.

Additional requirements:

- Never commit private keys, seed phrases, API keys, or funded-wallet credentials.
- Use dedicated development wallets containing testnet assets only.
- Use environment-variable examples with placeholder values.
- Ensure `.env`, wallet keypairs, build artifacts containing secrets, and local validator state are ignored by Git.
- Label the cross-chain relayer as trusted and experimental.
- Do not describe simulated rewards as real yield.
- Do not use the M0 `$M` token or imply that MinUSD is powered by, affiliated with, or endorsed by M0.

## 7. Users and stakeholders

- **Treasury manager:** Receives simulated product rewards.
- **Compliance operator:** Freezes or unfreezes accounts when authorized.
- **System administrator:** Pauses or resumes issuance and redemption.

### 7.2 Repository users

## 8. Conceptual architecture

MinUSD will use equivalent product semantics on both chains, but it will respect each chain's native execution model.

```text
                           MinWallet client / CLI
                         /                        \
                        v                          v
              Base Sepolia                     Solana Devnet
        Solidity contracts + ERC-20      Anchor program + token program
        - MockUSDC                       - MockUSDC mint
        - MINUSD token                   - MINUSD mint
        - Collateral vault               - Vault PDA/token account
        - Issuance controller            - Config/state PDAs
        - Rewards controller             - Program instructions
                        \                          /
                         v                        v
                    Event/log indexer and reconciler
                                 |
                                 v
                   Supply, collateral, and bridge status
```

### 8.1 Architectural principle

“Equivalent behavior” does not mean identical code:

- On EVM, Solidity contracts own persistent storage and call one another synchronously.
- On Solana, stateless programs receive explicit accounts, while persistent state and token balances live in separate accounts controlled by programs.
- The two implementations must expose comparable user flows and invariants while using native chain patterns.

## 9. Core domain model

### 9.1 Assets

- **MockUSDC:** A freely mintable test token used as simulated collateral. It has no monetary value.
- **MINUSD:** The branded token issued by the prototype against deposited MockUSDC.
- **Simulated rewards:** Newly mintable MINUSD accounted for separately and claimable only by the configured treasury.

### 9.2 Roles

- **Admin:** Assigns roles and changes approved configuration.
- **Pauser:** Pauses and resumes sensitive operations.
- **Compliance operator:** Freezes and unfreezes accounts.
- **Reward manager:** Accrues or configures simulated rewards.
- **Treasury recipient:** Receives claimed rewards.
- **Bridge relayer:** In the later cross-chain phase, submits destination-chain mint instructions after observing source-chain burns.

Admin roles should use separate development keys where practical. The documentation must explain that production deployments would normally use stronger controls such as multisignature authorization, timelocks, monitoring, and formal operational procedures.

### 9.3 Important invariants

For each chain:

- User acquisition increases MINUSD supply and vault MockUSDC by equal nominal amounts.
- Redemption decreases MINUSD supply and vault MockUSDC by equal nominal amounts.
- Ordinary transfers change holder balances but not total supply or collateral.
- A reverted transaction leaves no partial state changes or persisted events.
- Frozen accounts cannot participate in restricted flows.
- Paused operations cannot proceed.
- Claimed rewards cannot exceed recorded, unclaimed simulated rewards.

For the later multichain phase:

- A cross-chain transfer must not increase global circulating supply.
- Each source burn message may be consumed no more than once.
- Destination minting must use the amount and recipient committed in the source message.

## 10. Required user flows

### 10.1 Faucet and setup

1. User connects a dedicated test wallet.
2. User obtains native test gas from the relevant faucet.
3. User receives MockUSDC from the project's test faucet or mint helper.
4. Client displays native gas, MockUSDC, and MINUSD balances.

### 10.2 Acquire MINUSD on EVM

1. User calls `MockUSDC.approve(issuanceController, amount)`.
2. User submits an acquisition or `mintWithCollateral` transaction.
3. Controller checks pause state, account restrictions, amount, allowance, balance, and any configured cap.
4. Controller transfers MockUSDC from the user into the collateral vault.
5. Controller mints the equivalent nominal amount of MINUSD to the designated recipient.
6. Contracts emit standard transfer events and a domain-specific acquisition event.

If any check or downstream call fails, the entire transaction reverts.

### 10.3 Acquire MINUSD on Solana

1. User invokes the acquisition instruction with the required signer, mint, token accounts, vault, and program accounts.
2. Program validates account ownership, authorities, PDA derivations, pause state, account restrictions, amount, and any cap.
3. Program performs a CPI to move MockUSDC into the program-controlled vault token account.
4. Program performs a CPI to mint the equivalent nominal amount of MINUSD to the recipient's token account.
5. Program records or emits sufficient information for reconciliation.

No ERC-20 `approve` transaction is required merely because the EVM flow uses one. The Solana implementation should use the authority and account model appropriate to SPL tokens.

### 10.4 Transfer MINUSD

- Holder transfers MINUSD to another wallet.
- Sender balance decreases and recipient balance increases by the same amount.
- Total supply and collateral balances remain unchanged.
- The transfer fails when the contract/program is paused where applicable, either participant is frozen, the balance is insufficient, or required accounts/authorities are invalid.

### 10.5 Redeem MINUSD

1. User requests redemption for an amount of MINUSD.
2. System validates pause state, restrictions, balance, and available MockUSDC collateral.
3. MINUSD is burned from the holder.
4. The equivalent nominal MockUSDC amount is released from the vault to the designated recipient.
5. Redemption and token movement events/logs are recorded.

Redemption is an on-chain mock-collateral flow, not a fiat off-ramp.

### 10.6 Freeze and unfreeze

- An authorized compliance operator can freeze or unfreeze an address or its equivalent controlled state.
- A frozen account cannot acquire, transfer, or redeem MINUSD according to the documented policy.
- Unauthorized callers must fail.
- Administrative actions must be observable through events or logs.

### 10.7 Pause and resume

- An authorized pauser can halt acquisition and redemption during an incident.
- The PRD leaves transfer pausing as an explicit design decision to resolve before implementation.
- Unauthorized callers must fail.
- Resume restores the configured behavior.

### 10.8 Simulated treasury rewards

The initial rewards model follows a simple “yield to one” pattern:

1. Reward manager records or accrues a simulated reward amount.
2. Anyone may call `claimYield` if desired, but the configured treasury is always the recipient; alternatively, claiming may be permissioned if simpler for the first implementation.
3. The system mints no more than the accumulated, unclaimed amount.
4. Claimed amount is deducted from unclaimed reward accounting.
5. The token mint and reward-claim events/logs identify the amount and recipient.

The reward source is deliberately simulated. It does not represent actual interest earned by reserve assets.

### 10.9 Cross-chain transfer — post-MVP

The first cross-chain implementation will be a trusted burn-and-mint simulation:

1. User requests a transfer from a source chain to a destination chain.
2. Source implementation burns or escrows MINUSD and emits a message containing source chain, destination chain, nonce/message ID, sender, recipient, and amount.
3. Relayer observes a finalized source event or instruction.
4. Relayer submits the message to the destination implementation.
5. Destination verifies the trusted relayer and rejects previously consumed message IDs.
6. Destination mints the same amount to the specified recipient.
7. Reconciler marks the transfer complete and verifies the global supply invariant.

This phase must document finality assumptions, replay protection, failure recovery, and the trust placed in the relayer. It must not be described as a production bridge.

## 11. Functional requirements

### 11.1 EVM implementation

The EVM implementation must:

- Use Solidity and Foundry.
- Deploy to Base Sepolia after local tests pass.
- Use an ERC-20-compatible MINUSD token.
- Use MockUSDC with explicit decimal handling.
- Implement acquisition, transfer, redemption, pause, freeze, and simulated treasury rewards.
- Use role-based access control.
- Use custom errors or clear revert reasons.
- Emit domain-specific events for operationally important actions.
- Prevent obvious reentrancy and unsafe external-call ordering in collateral flows.
- Include unit, fuzz, negative-path, and invariant tests where appropriate.

### 11.2 Solana implementation

The Solana implementation must:

- Use Rust and Anchor unless a documented spike justifies a different native approach.
- Deploy to Solana Devnet after local-validator tests pass.
- Use SPL Token or Token-2022, with the final choice documented before implementation.
- Use PDAs for program configuration, vault authority, and other deterministic program-controlled state.
- Implement behavior equivalent to the EVM acquisition, transfer-policy, redemption, pause, freeze, and rewards flows.
- Validate signers, ownership, mint identity, token accounts, PDA seeds, and authorities.
- Include positive and negative integration tests through an Anchor or TypeScript test client.
- Produce logs and state that can be inspected in Solana Explorer or another documented explorer.

### 11.3 Client and scripts

The repository must provide a small TypeScript command-line client or scripts that can:

- Display configuration and balances.
- Obtain or mint MockUSDC in the test environment.
- Approve EVM collateral spending.
- Acquire, transfer, and redeem MINUSD.
- Claim simulated rewards.
- Print transaction hashes or Solana signatures and explorer links.
- Clearly report success, pending state, and decoded failures where possible.

A browser UI is optional and should not delay the contract/program work.

### 11.4 Reconciliation and observability

The project must eventually provide a read-only reconciliation command or service that reports:

- MINUSD total supply by chain.
- MockUSDC collateral held by each chain's vault.
- Unclaimed and claimed simulated rewards.
- Acquisition, redemption, freeze, and pause activity.
- Cross-chain burns, destination mints, pending messages, and consumed message IDs after the bridge phase exists.
- Any violated invariant or unexplained balance difference.

The initial implementation may be TypeScript. A later Python notebook or indexer is encouraged if it materially demonstrates event analysis and the author's data background.

### 11.5 Portfolio showcase

The portfolio release should include a lightweight browser-based **MinUSD Protocol Lab**. This is an interactive engineering case study and protocol explorer, not a polished consumer wallet or production banking interface. It should make the implementation, transaction lifecycle, operational controls, and author’s technical reasoning understandable to a reviewer in under five minutes.

The showcase should provide two clearly labeled modes:

- **Guided run:** Replays a documented lifecycle using saved data from real public testnet transactions. It must work without a wallet, test gas, or RPC writes.
- **Live testnet:** Allows a reviewer to connect a dedicated test wallet and submit supported transactions directly to Base Sepolia or Solana Devnet. All write transactions must be signed by the user’s wallet.

The guided run should demonstrate one coherent lifecycle with explicit before-and-after accounting:

1. Obtain or mint MockUSDC.
2. Approve collateral spending on EVM where required.
3. Deposit 100 MockUSDC and acquire 100 MINUSD.
4. Transfer part of the MINUSD to another account.
5. Redeem part of the MINUSD for MockUSDC.
6. Reconcile final balances, total supply, and vault collateral.
7. Inspect at least one deliberately failed transaction and prove that no partial state changes persisted.

For each selected lifecycle step, the showcase should display:

- Network or cluster and confirmation status.
- Signing wallet and recipient.
- Contract/program and function/instruction invoked.
- Human-readable inputs and outputs.
- Relevant events, logs, or account changes.
- Wallet, vault, reward, and total-supply deltas where applicable.
- Transaction hash or signature with an explorer link.
- A concise explanation of why the operation succeeded or failed.
- Links to the relevant source code and documentation where practical.

The portfolio view should include the following sections:

- **Project introduction:** Product narrative, educational disclaimer, source repository, and architecture summary.
- **Protocol health:** Per-chain MINUSD supply, MockUSDC vault collateral, simulated rewards, and reconciliation status.
- **Lifecycle explorer:** A step-by-step visualization of acquisition, transfer, redemption, and resulting accounting changes.
- **Transaction inspector:** Decoded call/instruction, signer, events/logs, state changes, status, and explorer evidence.
- **Failure lab:** Representative pause, freeze, authorization, allowance, balance, or replay failures with decoded errors and confirmation that state did not persist.
- **EVM versus Solana:** Side-by-side comparison of equivalent product behavior and the different contract, account, authority, call/CPI, event, and log models.
- **Engineering evidence:** Automated test and CI status, deployment addresses, architecture decisions, threat model, runbooks, and the narrated demo.

The interface must visibly label all data as testnet-only and distinguish saved demonstration data from live chain data. It must not imply that MinUSD has monetary value, real reserves, production security, or fiat redemption. The portfolio UI may read normalized event history and reconciliation results from the Python service, but the backend must not custody keys or sign user transactions.

The portfolio view should be implemented progressively after the underlying behavior exists:

1. Static case study using documented testnet evidence.
2. Live Base Sepolia balances and lifecycle actions.
3. Indexed event history, reconciliation, and failure inspection.
4. Solana lifecycle and multichain comparison.

The showcase must not become a prerequisite for completing the single-chain EVM contract MVP.

## 12. Transaction diagnostics requirements

Documentation must include a diagnostic playbook for both EVM and Solana.

### 12.1 Common intake fields

- Network/cluster.
- Transaction hash or signature, if one exists.
- Initiating wallet.
- Target contract/program.
- Intended function/instruction.
- Input and output assets.
- Amount and recipient.
- Expected result and observed result.
- Client timestamp and relevant application/RPC logs.

### 12.2 Diagnostic state model

#### No transaction hash/signature

Investigate the client, wallet, signing, serialization, RPC submission, connectivity, and preflight/simulation path. Nothing should be assumed to have reached consensus.

#### Pending or dropped

- **EVM:** Inspect nonce ordering, fee competitiveness, mempool visibility, replacement transactions, and RPC propagation.
- **Solana:** Inspect recent blockhash expiration, preflight results, RPC submission, leader/cluster congestion, prioritization fees, and confirmation status.

No contract/program execution should be inferred until the transaction is included and executed.

#### Reverted or failed

- Decode the function/instruction and arguments.
- Inspect revert reason, custom error, program error, simulation output, and logs.
- Check permissions/signers, balances, allowance where relevant, account ownership, supported assets, caps, pause/freeze state, slippage/deadline, and downstream calls/CPIs.
- Identify the exact failing call or instruction when traces are available.
- Confirm that attempted state changes did not persist.

#### Successful but wrong outcome

- Verify recipient, amount, token/mint, events/logs, balance deltas, total supply, vault collateral, and application assumptions.
- Distinguish blockchain success from business success.
- Record whether the issue is bad input, integration logic, configuration, or contract/program behavior.

### 12.3 Escalation package

An engineering escalation must contain:

- Reproduction steps.
- Transaction hash/signature and explorer link.
- Decoded call/instruction and relevant account addresses.
- Expected versus observed behavior.
- Events/logs, state and balance deltas, and exact failing step.
- Suspected cause, confidence level, and checks already completed.
- Customer impact, urgency, and any safe workaround.

## 13. Testing requirements

### 13.1 Minimum behavior coverage

Both chain implementations must test:

- Successful acquisition.
- Successful transfer.
- Successful redemption.
- Successful reward accrual and claim.
- Unauthorized administrative calls.
- Paused acquisition and redemption.
- Frozen sender and recipient behavior.
- Insufficient token balance.
- Insufficient collateral balance.
- Zero amount and invalid recipient behavior.
- Cap enforcement if caps are implemented.
- Decimal conversion and rounding behavior.
- Preservation of state when a transaction fails.

### 13.2 Invariant tests

At minimum, tests must demonstrate:

- Acquisitions and redemptions preserve the intended collateral-to-circulating-supply relationship, excluding explicitly recorded rewards.
- Transfers do not change total supply.
- Claimed rewards never exceed recorded unclaimed rewards.
- Unauthorized accounts cannot perform privileged actions.
- Failed operations do not leave partial accounting changes.
- A cross-chain message cannot be consumed twice once the bridge phase is implemented.

### 13.3 Test evidence

The repository should include:

- Automated test commands.
- Representative test output in CI.
- At least one public successful transaction per core flow and chain.
- At least one deliberately failed transaction per chain, with a written diagnosis.

## 14. Security model and threat analysis

The project must include a lightweight threat model before public testnet deployment. It should address:

- Compromised admin, pauser, compliance, reward, or relayer keys.
- Unauthorized minting or reward claims.
- Reentrancy and unsafe external calls on EVM.
- Incorrect token/mint, account substitution, missing signer, ownership, or PDA validation on Solana.
- Decimal mismatch and rounding errors.
- Insolvent mock-collateral vaults.
- Replay or duplicate cross-chain messages.
- Destination mint without finalized source burn.
- Pause/freeze abuse and recovery procedures.
- RPC failure, duplicate submission, and misleading client state.

Security documentation must separate safeguards actually implemented from production safeguards that are only recommended.

**Outcome:** One developer workflow can operate and inspect both implementations.

- Add a chain-aware balance, supply, collateral, and rewards report.

**Outcome:** A test user can move MINUSD between chains without inflating global supply.

- Implement source burn/message and destination mint/consume flows.
- Implement trusted relayer and message store.
- Add replay protection, finality rules, retries, and reconciliation.

**Outcome:** An external reviewer can understand, run, and evaluate the work.

- Polish README and technical documentation.

- Publish testnet addresses and representative transaction links.

### Optional Milestone 6 — DeFi savings vault

**Outcome:** Demonstrate how MINUSD could integrate with a tokenized vault without turning the project into a lending protocol.

- Add a test-only ERC-4626-style savings vault on EVM.
- Document the conceptual Solana equivalent rather than forcing identical standards.
- Keep rewards simulated and clearly separated from real yield.

## 17. MVP definition

The **single-chain EVM MVP** is complete when:

- Core EVM flows and controls work locally and on Base Sepolia.
- Automated positive and negative tests pass.
- Contract addresses and representative explorer links are documented.
- The author can explain every state change and event in one successful acquisition and one failed transaction.

The **multichain MVP** is complete when:

- Equivalent core flows work on Base Sepolia and Solana Devnet.
- A unified client can invoke and inspect those flows.
- Reconciliation reports per-chain supply and collateral.
- Documentation accurately compares the two execution models.

The bridge simulation is a subsequent milestone, not a prerequisite for demonstrating the foundational EVM/Solana competency.

The **portfolio showcase** is complete when:

- A reviewer can understand the product, architecture, and primary lifecycle without connecting a wallet.
- The guided run uses documented public testnet evidence and clearly identifies saved versus live data.
- Each lifecycle step exposes the signer, invoked code, events/logs, state changes, and explorer evidence.
- At least one failed transaction is decoded and shown to have persisted no partial state changes.
- Reconciliation visibly explains whether supply, collateral, and recorded rewards are consistent.
- Live actions, when enabled, require the reviewer’s wallet to sign every write transaction.

## 18. Success criteria

The project succeeds when:

- A new developer can run tests from the README without undocumented manual setup.
- All required lifecycle and failure-path tests pass in CI.
- Both testnet deployments can demonstrate acquire, transfer, redeem, administrative control, and rewards flows.
- Explorer evidence matches the documented balance and supply changes.
- No secrets or real-value assets are present in the repository.
- Cross-chain supply does not inflate and messages cannot be replayed if Milestone 4 is completed.
- The author can answer, using project evidence:
  - What state changed?
  - Which authority signed?
  - Which contract/program executed?
  - Which event/log confirms the result?
  - Why did a failed transaction fail?
  - How do the EVM and Solana implementations differ?
  - What would need to change before a production launch?

## 20. Decisions made

- The public product name is **MinUSD**; `MINUSD` avoids collision with the commonly used `mUSD` symbol.
- The primary narrative is a wallet/fintech product, not a DeFi lending protocol.
- The project is public, educational, testnet-only, and unaudited.
- Base Sepolia is the EVM test network.
- Solana Devnet is the Solana cluster.
- Solidity and Foundry are used for EVM.
- Rust and Anchor are the default Solana implementation approach.
- TypeScript is the default shared client language.
- Python is optional for later analytics and is not required for core contract development.
- The portfolio release includes a browser-based MinUSD Protocol Lab, implemented after the core contract flows and evidence are stable.
- The portfolio view supports a no-wallet guided run and may additionally offer wallet-signed live testnet interactions.
- The portfolio view is an engineering case study and protocol explorer, not a production consumer wallet.
- MockUSDC is the only initial collateral asset.
- Simulated treasury rewards are used instead of real yield.
- EVM and Solana implementations target equivalent behavior rather than identical internal architecture.
- The cross-chain phase uses an explicitly trusted simulation before any third-party messaging integration is considered.
- A DeFi vault is an optional extension after the wallet lifecycle and multichain foundations work.

## 21. Open decisions

Resolve these during Milestone 0 and record the outcomes in ADRs:

- Should ordinary MINUSD transfers stop when the system is paused, or only acquisition and redemption?
- Should `claimYield` be callable by anyone with a fixed treasury recipient, or only by an authorized role?
- Should EVM collateral custody live in the issuance controller or a separate vault contract?
- Should the EVM implementation use six or eighteen decimals for MINUSD, and how will conversions avoid rounding errors?
- Should the Solana implementation use the original SPL Token Program or Token-2022, and which extensions are genuinely useful?
- How should Solana freeze behavior interact with token-program freeze authority versus program-maintained restrictions?
- Should collateral caps be included in the first lifecycle MVP or introduced in a later iteration?
- What source-chain finality threshold is sufficient for the trusted relayer demonstration?
- Where should consumed cross-chain message IDs be stored on each chain?
- Is a CLI sufficient for the portfolio release, or would a minimal browser demo materially improve the presentation?

## 23. Definition of done for the public portfolio

The project is ready to feature on a resume or in an interview only when the author can demonstrate the implementation rather than merely point to generated code. Specifically, the author must be able to:

- Explain the purpose of every deployed component.
- Trace acquisition and redemption line by line at the transaction level.
- Explain why EVM requires allowance for a controller-driven `transferFrom` flow and how the Solana authority model differs.
- Diagnose one EVM revert and one Solana program failure without relying entirely on an assistant.
- Reconcile token supply, collateral, and simulated rewards.
- Identify the system's trust assumptions and most important security risks.
- Describe what is deliberately missing for production readiness.

The strongest portfolio outcome is not the number of features. It is a small, correct system whose behavior, limitations, and operational risks the author can explain precisely.
